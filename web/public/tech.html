The cost of a tickmodule

A reducer is a transaction. Sixty a second, per entity, adds up.

Running the simulation inside the module works, and SpacetimeDB is well able to host it. The question is what it costs. Every tick is a transaction, and at 60 Hz per car that is throughput spent integrating tire forces, resolving collisions and running bot AI rather than on everything else the database is doing for you.

The usual escape hatch is to let clients own their positions, which buys back the frame rate by giving away the security model. There is a third option, and it is the only one that keeps both: move the computation out, keep the authority in.

Neon Bay takes the middle column. The physics lives in a sidecar: an ordinary SpacetimeDB client that happens to be trusted, running the simulation in its own process at a fixed 60 Hz and writing the results back through a reducer only it is allowed to call.

The database still holds the one true answer.
It just stopped being the thing that computes it.

Inbox, registry, outboxmodule

The module becomes a mailbox with a schema.

Strip the simulation out and what is left is small enough to describe in three words. The module in this demo is 516 lines of Rust and contains no integrator, no collision code and not even a track. It is:

  • An inbox. input, one row per client, overwritten ~30 times a second, holding throttle, steering, brake, handbrake. The only thing a player is trusted to assert.
  • A registry. config, player, car: who is connected, which physics slot is theirs, and which identity is allowed to be the authority.
  • An outbox. car_state, one authoritative pose per car, written only by the sidecar, fanned out to every subscriber by the database.

A fourth table, lap_record, keeps best laps. That is deliberate: aggregating results is bookkeeping, not simulation, so it belongs in the database. The line to hold is not “nothing runs in the module”, it is nothing that runs every tick.

The trust gatemodule

Eight lines are the whole security model.

The sidecar is not privileged by the runtime. It authenticates like any other client and gets an ordinary Identity — the module owner's, which is the only one that can read a private table or claim the authority. What makes it the authority in the moment is that the module wrote down which connection holds the lease, and checks that.

module/src/lib.rsthe entire trust boundary
/// Claim the right to publish authoritative state. Two questions, and they are
/// different ones. *May* you be the authority: only the identity that published
/// the module. *Can* you have it right now: only if the seat is empty, already
/// yours, or its holder has gone quiet for a lease.
#[reducer]
pub fn claim_authority(ctx: &ReducerContext, physics_fingerprint: u32) -> Result<(), String> {
    let mut cfg = config(ctx);
    let me = ctx.connection_id().ok_or("needs a live connection")?;

    // `None` only on a database older than this column, where the first claim pins it.
    if cfg.owner.is_some_and(|owner| owner != ctx.sender()) {
        return Err("not the database owner".into());
    }
    if let Some(held) = cfg.holder {
        let quiet = ctx.timestamp.to_micros_since_unix_epoch()
            - cfg.updated_at.to_micros_since_unix_epoch();
        if held != me && quiet < LEASE_MICROS {
            return Err("another sidecar holds the lease".into());
        }
    }
    cfg.sidecar = Some(ctx.sender());
    cfg.holder = Some(me);
    cfg.physics_fingerprint = physics_fingerprint;
    cfg.updated_at = ctx.timestamp;
    ctx.db.config().id().update(cfg);
    Ok(())
}

/// The fence. Holding the right identity is not enough -- a sidecar that was
/// replaced while it was away still has it -- so what is checked is the
/// connection recorded by the winning claim.
fn require_authority(ctx: &ReducerContext) -> Result<Config, String> {
    let cfg = config(ctx);
    if cfg.holder.is_some() && cfg.holder == ctx.connection_id() {
        Ok(cfg)
    } else {
        Err("only the sidecar holding the lease may write simulation state".into())
    }
}

Every reducer that writes simulation state (push_states, spawn_bot, despawn_bot) opens with require_authority(ctx)?. Every reducer a player can reach does not, because none of them touch a position. The complete client-facing hot path is one reducer:

Who is allowed to be the authority

One identity, fixed when the module is published. init runs as whoever published it and writes that identity into config; claim_authority refuses anyone else. A player cannot appoint themselves the authority, and the restart window after a deploy is an opening only for the next process holding that identity's token. It is the same identity that reads the inbox: input is a private table, which SpacetimeDB shows to the database's owner and to nobody else, so a player subscribing to a rival's controls is told the table does not exist.

Anatomy of a ticksidecar

Connect, claim, then never stop.

Startup is two steps: connect with the owner's token, and subscribe to the five tables the simulation touches. Claiming the lease, resuming the tick counter from config.server_tick and filling the grid with bots all happen the moment the database grants the authority — which may be immediately, or may be when the sidecar currently holding it goes away. Until then the process stands by, adopting each snapshot as it lands so that a promotion is a continuation rather than a restart.

sidecar/src/authority.rsone simulation tick
pub fn step(&mut self, conn: &DbConnection) {
    self.sync_cars(conn);         // reconcile slots against the `car` table
    self.check_authority(conn);   // ours? claim it, or follow whoever has it
    self.pull_inputs(conn);       // promote whatever is due this tick
    if !self.has_authority {
        return;                  // standing by: the holder's snapshots are the truth
    }
    self.drive_bots();            // the AI that would otherwise cost transactions

    self.world.step(self.world.active);

    if self.world.tick % SNAPSHOT_EVERY == 0 {
        self.publish(conn);       // every 3rd tick: 60 Hz / 3 = 20 Hz
    }
}

Pull, don't subscribe to callbacks

The obvious way to consume input is on_insert/on_update handlers. This sidecar doesn't. Each tick it just iterates the materialized view the SDK already keeps for it, conn.db.input().iter(), and reads what is there right now.

With a couple of dozen rows that costs nothing and removes an entire class of ordering bug: there is no queue to drain, no event that can land mid-step, no lock between a callback thread and the simulation. The loop is single-threaded and reads a consistent snapshot at a point it chose. Worth copying unless your row count makes a full scan expensive.

Scheduling inputssidecar

An input is stamped with the tick it drives, and waits for it.

This is the detail that turns “close enough” prediction into exact prediction, and it is easy to miss. The client runs a few ticks ahead of the authority and stamps every input with the tick it belongs to. The sidecar does not apply inputs on arrival. It queues them and promotes each one when its own clock reaches that tick.

sidecar/src/authority.rs · pull_inputspromote what is due
// `world.tick` is still the pre-step value: the input for tick T is the one
// applied during the step that takes the world from T to T+1, the same
// convention the client uses.
let now = self.world.tick;
for slot in 0..MAX_CARS {
    let Some(state) = self.slots[slot].as_mut() else { continue };

    while state.pending.front().is_some_and(|(t, _)| *t <= now) {
        state.current = state.pending.pop_front().unwrap().1;
    }
    // Nothing due but a backlog waiting means the client clock drifted
    // behind us; take the oldest rather than stall.
    if state.pending.len() > 12 {
        state.current = state.pending.pop_front().unwrap().1;
    }
    self.world.inputs[slot] = state.current;
}

Three cases, all handled: an input that arrives early waits for its tick. One that arrives late is applied immediately (there is no rewinding the authority) and the client absorbs the difference on its next rollback. One that never arrives leaves state.current holding the last controller reading, which is why packet loss shows up as the authority briefly disagreeing rather than the car cutting its engine.

The queue is capped at 64 entries so a client with a wildly wrong clock cannot make the sidecar allocate forever, and set_input in the module rejects any sequence number it has already seen, so a reordered packet can never walk the controls backwards. It also spends from a token bucket — 45 writes a second, 15 banked — so a client sending faster than the browser does has the excess dropped before the row is written, and therefore before any subscriber pays to hear about it.

The client halfbrowser

Predict, reconcile, smooth.

Everything so far works without a line of client-side physics: subscribe to car_state, interpolate, draw, and accept the lag. You need this section only if the latency between an input and its visible effect matters. In a racing game it does.

  1. Predict Every tick, sample the controls, step the local car in wasm immediately, and store (tick, input, resulting state) in a 256-entry ring buffer. Steering has zero input lag regardless of ping.
  2. Reconcile A snapshot arrives carrying the authority's state for some tick T in the recent past. Compare it against what was recorded for T. If they differ by more than 1.5 mm, rewind to the authoritative state and replay the stored inputs from T+1 to now, typically 5 to 20 ticks and about 20 µs of work.
  3. Smooth A rewind moves the car, which would read as a stutter. Instead keep the difference between where the car appeared to be and where it now is as a visual offset, and decay that to zero over ~220 ms. The simulation is corrected instantly; the picture catches up.

The clock is what has to be right

For prediction to be exact, an input stamped for tick T must be applied by the authority at tick T. So the client estimates where the sidecar's clock is now, adds a round trip plus two ticks of margin, and steers its own tick rate by up to ±6 % to hold that lead, a time dilation you cannot feel. Other cars are predicted colliders, not simulations

The client never simulates a rival, but it does predict one. The local car is deliberately in the future — far enough ahead that its input arrives before the tick it belongs to — so holding a rival a few ticks in the past, which is what an interpolation buffer does, puts it wrong by the sum of the two: several metres at racing speed, always behind. Instead each rival is carried forward from its newest published pose to the tick actually being simulated, at a constant turn rate, which follows a car through a corner instead of flying off the tangent. Measured against the snapshots that arrive next, that is 0.14 m of error over a tenth of a second of lead, and whatever a snapshot does reveal is faded out rather than snapped.

The predicted rivals are parked in the wasm world as immovable colliders, so you can lean on someone mid-corner and your own prediction reacts at once, while never claiming to own their state. World::step takes a simulation mask for exactly this: the sidecar passes every car, the browser passes only its own. A rollback puts the rivals back where they were at each replayed tick, so the contact being replayed is the one the authority resolved.

Determinismbrowser

One crate, compiled twice, agreeing bit for bit.

The physics is a single dependency-free crate built two ways: an rlib linked into the native sidecar, and a cdylib for wasm32-unknown-unknown loaded by the browser. Not a port, not a reimplementation. That is what makes the measured prediction error zero rather than small.

Two things get in the way of that, and both need handling:

  • Transcendentals. libm's sinf on x86-64 and the one linked into a wasm module are not guaranteed to agree in the last ulp, and one ulp compounds over a few hundred ticks into a visible desync. So sin, cos, atan and atan2 are hand-rolled polynomials evaluated with nothing but +, - and *, which are IEEE-754 exact everywhere. sqrt is correctly rounded by the standard and is used directly.
  • FMA contraction. If the compiler fuses a * b + c into a single multiply-add, the native build rounds once where wasm, which has no FMA instruction, rounds twice. Rust does not contract by default, so the rule is simply: never build this workspace with -C target-cpu=native.
Verify it, don't assume it

node scripts/verify-determinism.mjs runs the same 1200-tick scripted race through both builds and diffs the raw f32 bits at ten checkpoints. A determinism claim you do not test is a determinism claim that will quietly stop being true.

Same source is a build-time fact. Deploys are not.

That check proves something about the machine that built the two halves. It says nothing about the pair actually talking to each other. The sidecar ships to a container and physics.wasm ships to a CDN, and nothing makes those two things happen together: a cached bundle, a rolled-back service, a deploy that only half succeeded.

When they diverge, nothing errors. The client predicts with the physics it has, the authority decides with the physics it has, and every corner ends in a correction that looks exactly like packet loss. It is the worst failure mode this architecture has: silent, and it points at the network.

So each side scores itself at startup. Not a version string, which records only what someone remembered to bump. A 240-tick scripted race, hashed down to one u32 from the raw bits it ends on. Two builds match if and only if they agree on the arithmetic: a refactor that changes nothing observable still matches, and moving one constant does not. The sidecar hands its number to claim_authority, the module publishes it in config without opinion, and the browser compares it against its own.

physics/src/fingerprint.rswhat this build computes, as one number
pub fn fingerprint() -> u32 {
    let mut w = World::new();
    w.spawn(0, 0);
    w.spawn(1, 3);
    for tick in 0..TICKS {
        w.inputs[0] = scripted(tick);
        w.inputs[1] = scripted(tick + 511);
        w.step((1 << CARS) - 1);
    }
    hash(&w)  // shape constants, then every f32 bit the race ended on
}

The browser scores itself inside phys_init, where the module is still allowed to allocate. Doing it lazily would grow linear memory and detach every Float32Array mapped over the old buffer. A mismatch turns the authority readout red and says so in the console, naming both numbers, because “your prediction is wrong” is not an actionable thing to tell someone and “redeploy these two together” is.

The same number is the first row verify-determinism.mjs diffs, so the check that guards the deploy is itself verified by the run that verifies the physics underneath it.

Getting state across the boundary for free

CarState is #[repr(C)] and entirely f32, 24 of them, so the browser maps it with a single Float32Array over wasm linear memory and reads and writes the simulation in place, with no serialization on the hot path. The whole core is a 38 KB .wasm with zero imports: no wasm-bindgen, no wasm-pack, no build plugin. All allocation happens inside phys_init, so nothing later grows memory and detaches the views.

Restartssidecar

The outbox is the save file.

A sidecar holds all the simulation state in memory, which sounds like the fragile part. It isn't, because everything the integrator reads back is already on the wire. Kill the process and start it again and it will:

  • re-claim authority, since the previous holder is now disconnected;
  • resume the tick counter at config.server_tick + 1, because starting from zero has the module silently reject every snapshot as out of order;
  • adopt every car from its last published car_state row: position, velocity, steering angle, lap, the lot;
  • reconcile the bot field back to its configured count, keeping whoever is already out there.

Drivers keep their momentum through a restart. What is missing is a hot standby: there is a visible gap while the process comes up, and nothing arbitrates between two sidecars racing to claim after a network partition.

The general lesson for your own sidecar: publish enough state to resume from. The two fields this simulation does not put on the wire (slip_f, slip_r) are overwritten before they are ever read, so reconstructing them as zero is exact rather than approximate. That is a property worth checking deliberately, not assuming.

Deploy them together

Database and sidecar talk on the hot path: every input as it lands, twenty snapshots a second, at a fixed 60 Hz that cannot slip. In this demo they ship as one container so that link stays on loopback instead of becoming a network. The browser client is static and goes to the edge separately; its only conversation is one wss:// back to the pair.

Build your ownany workload

The pattern, minus the cars.

Nothing above is specific to vehicle dynamics. The same shape fits pathfinding, economy simulation, matchmaking, procedural generation, ML inference: anything that is expensive, runs continuously, and must stay authoritative. The recipe:

  1. Split the schema into inbox, registry, outbox Clients write intent to the inbox. The registry says who is who and which identity may write results. The outbox holds the computed truth and nothing else writes to it.
  2. Gate the result reducer on identity One require_authority(ctx)? at the top of every reducer that writes results. Store the authorized identity in a config row, or bake it in at publish time rather than letting it be claimed.
  3. Make the sidecar an ordinary client Same SDK, same subscriptions, same auth. Nothing about it is privileged except the row with its identity in it.
  4. Pull state, don't wire callbacks Read the subscription cache at a point your loop chooses. It is a consistent view, it costs nothing at modest row counts, and it deletes a class of ordering bug.
  5. Batch the writes One reducer call carrying every changed entity, at a rate below your compute rate. Here that is 20 Hz snapshots against a 60 Hz simulation, a third of the transactions for the same fidelity.
  6. Publish enough to resume from If the outbox is a complete description of your computation's state, a restart is a hiccup instead of a reset. Check that claim explicitly.
  7. Decide whether clients predict Only if input-to-pixel latency matters. If it does, the same source has to run on both sides, which makes determinism a hard requirement and a thing to test in CI.
  8. Have both sides prove they agree If clients predict, the two halves deploy separately and will eventually be deployed apart. Score each build by what it computes, a fixed scripted run hashed down to a number, publish the authority's, and have clients check their own. Otherwise a stale bundle is indistinguishable from a bad network.

Honest gapsproof of concept

What this does not solve.

  • A standby has to be running to be one. A second sidecar stands by for 18 µs a tick, and when the authority is killed outright the authoritative stream goes quiet for 103–123 ms against the 50 ms that separates two snapshots anyway — the database settles who holds the lease. But this deployment ships one container with one sidecar in it, so a restart is still a gap of however long a process takes to come up. Two containers against one database is the fix, and nothing is in the way of it.
  • Contact is still resolved on the authority's timeline. Every car in the browser lives on one clock, so what you see, what you lean on and what the authority computes are the same arrangement of cars. What is left is that predicting a rival is a guess: 0.14 m out at a tenth of a second of lead, more when one brakes hard or is hit. Rewinding every rival into the view the toucher had is a much larger piece of work, and one most racing games decline — two cars cannot both be right about a mutual impulse.
  • The rate limiter still runs the reducer. A flood is dropped before it writes a row or fans one out, which is the part that costs everyone else. The transaction is still opened; bounding that is the host's job, not the module's.
  • The tick boundary spins. Measuring what the scheduler actually needs rather than guessing keeps it to 1.5 % of a core instead of 7 %, but a spin is a spin. Zero needs a timer the operating system does not portably offer.
  • One track, 24 slots, one database. The grid size is a constant shared by the module and the physics crate, and the sidecar refuses to start if the two disagree. Sharding across databases is not attempted.
